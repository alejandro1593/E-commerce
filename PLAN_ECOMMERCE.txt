  1. STACK TECNOLÓGICO Y JUSTIFICACIÓN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FRONTEND:
─────────
  → React 19 + Vite 6
    ¿Por qué? React es el estándar de la industria. Vite es 10-100x más rápido
    que webpack. React 19 trae Server Components y mejoras de rendimiento.

  → Tailwind CSS 4
    ¿Por qué? Utility-first CSS que acelera el desarrollo. Sin conflictos de
    nombres de clases. Se usa en el 60%+ de proyectos modernos.

  → Zustand (gestión de estado)
    ¿Por qué? Más ligero y simple que Redux. Solo 1KB. Perfecto para carrito
    de compras y estado global del UI.

  → React Router 7
    ¿Por qué? Navegación SPA estándar. Soporte para layouts anidados.

  → Axios + React Query (TanStack Query)
    ¿Por qué? Cache inteligente de datos, refetch automático, manejo de
    loading/error states sin boilerplate.

BACKEND:
────────
  → Node.js 22 LTS + Express 5
    ¿Por qué? Express sigue siendo el framework más popular y estable.
    Express 5 trai soporte nativo para async/await (sin try/catch wrapper).
    Node 22 tiene soporte LTS hasta 2027.

  → Prisma 6 (ORM)
    ¿Por qué? Type-safe, migraciones automáticas, schema como fuente de verdad,
    relations claras. Es el ORM moderno estándar para Node.js.

  → PostgreSQL 16
    ¿Por qué? Base de datos relacional más avanzada del mundo open-source.
    ACID, soporte JSON,全文 search, extensible. Ideal para e-commerce donde
    la integridad de datos es CRÍTICA (inventory, orders, payments).
    No usar MongoDB: un ecommerce necesita transaccionesACID y relaciones
    estrictas (un producto tiene Variant, un Pedido tiene Items, etc.)

  → Redis 7
    ¿Por qué? Cache de sesiones, rate limiting, carrito temporal, cola de
    jobs. Es el estándar para caché en producción.

AUTENTICACIÓN Y SEGURIDAD:
──────────────────────────
  → JWT (access + refresh tokens)
  → bcrypt para passwords
  → Helmet.js para headers de seguridad
  → CORS configurado
  → Express Rate Limit
  → Express Validator para sanitización

PAGOS:
──────
  → Stripe (principal) + Mercado Pago (alternativa LATAM)
    ¿Por qué? Stripe es el estándar global. SDK oficial para Node.js,
    webhooks, manejo de suscripciones y reembolsos.

FILE STORAGE:
─────────────
  → Cloudinary o AWS S3
    ¿Por qué? Imágenes de productos optimizadas, CDN global, transforms
    on-the-fly (resize, format, quality).

EMAILS:
───────
  → Nodemailer + SendGrid/Resend
    ¿Por qué? Transaccionales (confirmación de compra, envío, etc.)

DEVOPS:
───────
  → Docker + Docker Compose
  → GitHub Actions (CI/CD)
  → ENV variables con dotenv

  4. API ENDPOINTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BASE URL: /api/v1

AUTH:
  POST   /auth/register        → Registrar usuario
  POST   /auth/login           → Login (retorna tokens)
  POST   /auth/refresh         → Refrescar access token
  POST   /auth/forgot-password → Enviar email de recuperación
  POST   /auth/reset-password  → Resetear contraseña
  POST   /auth/logout          → Logout (invalidar refresh)

USERS:
  GET    /users/me             → Perfil del usuario autenticado
  PUT    /users/me             → Actualizar perfil
  GET    /users/me/addresses   → Listar direcciones
  POST   /users/me/addresses   → Crear dirección
  DELETE /users/me/addresses/:id → Eliminar dirección

PRODUCTS (públicos):
  GET    /products             → Listar (paginado, filtros, search)
                                ?page=1&limit=20&category=slug&sort=price
                                &minPrice=10&maxPrice=100&search=keyword
  GET    /products/:slug       → Detalle de producto
  GET    /products/featured    → Productos destacados
  GET    /products/related     → Productos relacionados (?slug=, misma categoría)

CATEGORIES (públicas):
  GET    /categories           → Árbol de categorías
  GET    /categories/:slug     → Productos de una categoría

REVIEWS:
  GET    /products/:id/reviews → Reviews de un producto
  POST   /products/:id/reviews → Crear review (auth required)

CART:
  GET    /cart                 → Obtener carrito del usuario
  POST   /cart/items           → Agregar item al carrito
  PUT    /cart/items/:id       → Actualizar cantidad
  DELETE /cart/items/:id       → Eliminar item del carrito
  DELETE /cart                 → Vaciar carrito

WISHLIST:
  GET    /wishlist             → Listar favoritos del usuario
  POST   /wishlist/:id         → Toggle favorito (agrega/elimina)

UPLOADS (admin):
  POST   /uploads/images       → Subir imagen a Cloudinary (multipart)

COUPONS:
  POST   /cart/coupon          → Aplicar cupón al carrito
  DELETE /cart/coupon          → Remover cupón

ORDERS:
  POST   /orders               → Crear orden desde carrito
  GET    /orders               → Historial de órdenes del usuario
  GET    /orders/:id           → Detalle de orden
  POST   /orders/:id/cancel    → Cancelar orden

PAYMENTS:
  POST   /payments/create-intent → Crear PaymentIntent (Stripe)
  POST   /payments/confirm       → Confirmar pago
  POST   /webhooks/stripe        → Webhook de Stripe (sin auth)

ADMIN (/admin):
  GET    /admin/dashboard       → Estadísticas (ventas, usuarios, pedidos,
                                  top productos, stock bajo, ventas por día)
  GET    /admin/export/:type    → Exportar CSV (orders | products | users)
  GET    /admin/products        → CRUD productos
  POST   /admin/products
  PUT    /admin/products/:id
  DELETE /admin/products/:id
  GET    /admin/orders          → Todas las órdenes
  PUT    /admin/orders/:id/status → Cambiar estado
  GET    /admin/users           → Listar usuarios
  PUT    /admin/users/:id       → Activar/desactivar
  POST   /admin/coupons         → CRUD cupones
  PUT    /admin/coupons/:id
  DELETE /admin/coupons/:id

  5. FLUJOS PRINCIPALES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FLUJO DE COMPRA:
───────────────
  1. Usuario navega productos (GET /products con filtros)
  2. Agrega al carrito (POST /cart/items)
  3. Aplica cupón opcional (POST /cart/coupon)
  4. Inicia checkout
     a. Crea PaymentIntent (POST /payments/create-intent)
     b. Confirma pago con Stripe (frontend Stripe Elements)
  5. Webhook de Stripe confirma pago (POST /webhooks/stripe)
     a. Backend crea la Order con status CONFIRMED
     b. Reduce stock de productos
     c. Vacía el carrito
     d. Envía email de confirmación
  6. Usuario ve página de éxito con número de orden

FLUJO DE AUTENTICACIÓN:
───────────────────────
  1. Register → bcrypt hash → guardar user → crear tokens
  2. Login → verificar password → retornar access + refresh tokens
  3. Access token expira (15min) → usar refresh para obtener nuevo
  4. Refresh token expira (7d) → re-login

ESTADOS DE ORDEN:
─────────────────
  PENDING → CONFIRMED → PROCESSING → SHIPPED → DELIVERED
     ↓
  CANCELLED

FLUJO DE PRODUCTO (Admin):
─────────────────────────
  1. Admin crea producto con imágenes
  2. Imágenes subidas a Cloudinary
  3. Producto guardado con URLs de imágenes
  4. Variantes (talla, color) con stock individual

  6. SEGURIDAD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✓ Passwords hasheados con bcrypt (12 rounds)
  ✓ JWT con access (15min) + refresh tokens (7d)
  ✓ Rate limiting (100 req/15min general, 5 req/15min auth)
  ✓ Helmet.js para security headers
  ✓ CORS configurado (solo frontend permitido)
  ✓ Input validation con Zod en todos los endpoints
  ✓ SQL injection impossible (Prisma ORM parametriza queries)
  ✓ XSS protection (React escapa por defecto)
  ✓ CSRF tokens para form submissions
  ✓ Stock validation con transacciones (evitar overselling)
  ✓ Environment variables nunca commiteadas (.env.example)

  10. PRINCIPIOS DE DISEÑO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  • Feature-based architecture: cada módulo es autocontenido
  • Service layer: lógica de negocio separada de controllers
  • Validation at boundary: Zod valida en routes, nunca confiar en input
  • Fail fast: errores tempranos con mensajes claros
  • Idempotent webhooks: Stripe puede reenviar eventos
  • Optimistic updates en frontend: UX instantánea con rollback
  • Type safety end-to-end: TypeScript en backend Y frontend
  • No wildcard imports: tree-shaking friendly
  • Single source of truth: Prisma schema es la fuente de verdad de BD
